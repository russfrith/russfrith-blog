A3 investigation note -- an order-of-magnitude discrepancy found and corrected:
the original (Phase 1) version of this file called `cpuBound(2_000_000_000)` and
discarded the return value, printing only the elapsed time. That version reported
332ms for 2,000,000,000 iterations. Re-running the SAME 2,000,000,000-iteration
workload with the result printed (so the loop can't be proven dead and removed)

Conclusion: the original Go result was invalid -- the Go compiler's dead-code
elimination had removed (or substantially optimized away) a loop whose result was
never used. This was NOT a genuine ~8x Go-vs-Node speed advantage; once both
print the result, Go (404ms) and Node (411ms) are nearly identical for the same
300,000,000-iteration workload. Kotlin coroutines on Dispatchers.Default and Rust
async tasks using spawn_blocking behave the same qualitative way (heartbeat keeps
ticking without explicit offloading) as this Go counterexample; neither was run as
a full separate timed demo here, per the rule of showing full detail only where
something notable happens -- the "notable" thing for Rust/Kotlin in this scenario
is the scheduling behavior, not a timing comparison.
